# EPG, playlists and channel matching

Moved here from `agents.md` on 2026-10-22, verbatim. `agents.md`
points at this file; read it before changing the code it names and
grep it for the module, symbol or error you are about to touch.

- M3U and EPG display names are stored in `playlist_names` / `epg_names` mappings keyed by `playlist.source_name_key()` (SHA-256 of the original source). Keep source strings intact for existing loaders/caches. Provider names remain in their source dictionaries. Managers copy editable state so Cancel cannot change the live configuration; names are accepted with `GetNames()` alongside `GetResult()`.
- Playlist scope must include plain M3U URL/file strings using stable hashed IDs as well as provider IDs. Associate each completed playlist future with its actual source, and tag both cached and fetched channels; never use a leftover loop variable. Category counts and rows must use the scoped sources. The full browsing Tab cycle is Playlist view, categories, search, channels, on-air episode description, stream URL, reversed by Shift+Tab. The description comes before the URL and is always present; the URL field is optional and, when hidden, Tab from the description hands over to wx traversal so it wraps. Never point a Tab handler at a control that may be hidden - SetFocus on a hidden window silently does nothing and strands the user. Never trap traversal in just the playlist/category/channel controls. Category Tab activates the category then focuses search; Enter activates and focuses channels. Run `tools/smoke_playlist_navigation.py` after changing this wiring.
- EPG auto-import should be based on usable joined EPG data and source freshness, not just the presence or mtime of `epg.db`. `_ensure_db_tuned()` must not create an empty placeholder database.
- XMLTV reimports must replace stale titles and overlapping programme slots for the same channel ID. A correct feed on tv.serrebiradio.com was still shown as unrelated shows because the old `insert_programme` upsert changed only descriptions; 74 of 145 live Sky channels disagreed with the local database on 2026-09-27. An import lock with a dead owner PID must be reclaimed promptly rather than waiting two hours.
- EPG matching must account for country-specific channel aliases and suffixes, especially AU/CA/IE/UK/US sources. IPTV-org style XMLTV IDs with `@` suffixes need expansion for better channel matching.
- XMLTV downloads can resume, but HTTP 416 means the local partial file is already complete or invalid for that source; the downloader has fallback logic for this and should keep it.
- **urllib sends no `Accept-Encoding`, so an EPG feed arrives uncompressed unless we ask.** tv.serrebiradio.com (Dispatcharr) gzips `xmltv.php` *only* when the client sends `Accept-Encoding: gzip`; without it the response is 542 MB of plain XML, `Transfer-Encoding: chunked` with **no Content-Length**, which took ~54 s and reliably died mid-transfer with `[WinError 10054]`. Adding the header gives 44 MB in ~9.5 s (12.2x), same payload. Note the importer's `is_gz` check does see `Content-Encoding: gzip` and wraps the response in `gzip.GzipFile`, so no other change was needed - the robust resume/temp-file path is still keyed on the `.gz` *suffix* only, which this URL does not have. Keep the header on every EPG request, not just this source.
- Winsock aborts must stay in `_is_transient_epg_error` (module level, so it is testable; the importer's nested `_is_transient_stream_error` just delegates). urllib reports them as `[WinError 10054]`/`10053`/`10055`/`10051` text, which never matches the POSIX wording (`connection reset`) the old hint list looked for, so every one of them skipped the retry path and surfaced as "Failed to import EPG source". Do not narrow the hint list back to English-only phrases.
- A **partial** EPG import is silent and looks like a feed or matching failure. Because the 542 MB uncompressed transfer died on `10054` after the first ~15,000-batch commit, the database held 135,000 of the feed's 1,429,899 programmes (9%) while 45,551 of 47,532 channel rows (95.8%) had zero programmes. `resolve_best_channel_id` then made it look like a matcher bug: it scored "Judge Judy" at 96 but reordered on `_has_any_schedule_from_now` and returned "Judge Nosey" at 4, because Judy's real ids had no data while the wrong candidate did. Diagnose with `SELECT COUNT(*) FROM programmes` and `COUNT(DISTINCT channel_id) FROM programmes` before touching matching code -- a healthy import is within a few percent of the feed's own `<programme>` count. After the gzip header a full import is ~87 s for all 1,429,899 programmes, and the rebuilt database reports 98.9% coverage (499 of 47,532 rows empty, those being ids the feed itself never programmes).
- A provider's live channel and its EPG feed are independent: `https://tv.serrebiradio.com/live/<user>/<pass>/<id>` returned `HTTP 503 {"error": "Channel is stopping, retry shortly"}` and then read-timeouts while `xmltv.php` on the same account worked fine. When a user reports a broken stream and a broken guide together, probe both before assuming one cause.
- **Deleting `epg.db` alone does not wipe the EPG.** In WAL mode the committed data still lives in `epg.db-wal`, and the next open replays it back: a user deleted a 4 KB `epg.db`, and opening the database resurrected 47,533 channels and 135,000 programmes from a 136 MB `-wal` that had to be deleted too. Any "reset my EPG"/repair path and any support instruction must remove `epg.db`, `epg.db-wal` and `epg.db-shm` together, with no app running.
- An EPG database only ever grew because SQLite never returns the pages a `DELETE` frees to the filesystem, so `prune_old_programmes` cut the rows but not the file (one user's guide reached 8 GB). `PRAGMA auto_vacuum=INCREMENTAL` plus `incremental_vacuum` after the prune fixes it, with two traps: the pragma is only accepted **before the database file is created**, so it must stay the first entry in `PRAGMA_IMPORT` (`journal_mode=WAL` writes the header and makes it a silent no-op afterwards), and `PRAGMA incremental_vacuum` returns rows, so the statement must be drained (`.fetchall()`) or the connection is left with a statement in progress. Both only apply to databases created after the change; an existing file silently keeps `auto_vacuum=NONE` until it is rebuilt.
- Do **not** "optimise" `prune_old_programmes` into `WHERE start < ? AND end < ?` to use `idx_programmes_start_cover`. `EXPLAIN QUERY PLAN` says `SEARCH ... USING INDEX` instead of `SCAN programmes`, which looks like a win, but the measured `DELETE` was **7x slower** (0.93 s -> 6.38 s on 400k rows): a covering index does not avoid the table lookup for the delete itself, it only adds index churn. The plain full scan is the faster plan here.
- Xtream playlists and Dispatcharr's XC output mark archive channels `catchup="xc"` with no `catchup-source`; the archive URL is implied by the live URL. `_xtream_timeshift_url` turns `/live/U/P/ID` (or `/U/P/ID`) into `/timeshift/U/P/<minutes>/<YYYY-MM-DD:HH-MM>/<ID>.ts`. The start's clock comes from the `#EXTM3U` header's `catchup-timezone` (stored on each catch-up channel; Dispatcharr sends "UTC" and its archive parses the start as UTC), else the user's local time. Verified against a live Dispatcharr server, which answers 206 `video/mp2t`.
- `finish_import_background` records the hash of the source list the import actually read (`_epg_import_sources`), not the live `self.epg_sources`, and starts another import when they differ. A guide added while an import ran (EPG Manager, a playlist refresh) had its import refused and was then recorded as imported, so it waited for the next scheduled import.
- Plain M3U playlists (URL or file) contribute the guides their `#EXTM3U` header names (`x-tvg-url`, alias `url-tvg`; comma-separated, http(s) only, first line only) through `_playlist_header_epg_urls` into `self.playlist_epg_by_source` (per playlist, merged by `_merge_playlist_header_guides`, so an F5 refresh of one playlist replaces only its own guides) and the flattened `self.playlist_epg_sources`, kept apart from `provider_epg_sources` so `use_playlist_epg` (EPG Manager checkbox, default on) can drop them. `reload_epg_sources` dedupes on stripped text, so a playlist naming the guide the user already added (Dispatcharr's xmltv.php) is imported once. Providers keep their own `auto_epg`. EPG Manager edits only `config["epgs"]`: it used to receive the merged `self.epg_sources` and save it back, which made discovered provider guides permanent.
- The parsed-playlist cache is keyed by `_playlist_text_hash`, which is salted with `_PARSED_PLAYLIST_CACHE_VERSION`. Bump it whenever the parser produces different channel dicts from the same text, or users keep the old dicts until the provider's playlist changes.
- An exact tvg-id hit is a channel's own guide. `resolve_best_channel_id` returns it when it has data from now; when it has none, only a guide channel of the same canonical name may stand in, never a fuzzy candidate. Before this, fuzzy bonuses (implicit East +38, brand +50, region +18) outscored the exact id's 100, and the has-data-first sort let any candidate beat an empty own guide: on a 49,552-channel Dispatcharr playlist 3.5% of View EPG lookups showed another channel's schedule ("Cheers" showed National Geographic). An exact-name hit must not relabel an exact-id candidate either (exact-name +number scores 104).
- Channel-row labels and the description field are keyed by `_now_playing_key` (canonical name plus tvg-id), not the name alone: providers carry many same-named channels with different guides, and all of them read the first one's programme. The guide-side matcher (`channel_identity.match_guide_channel`) only falls back to names when the tvg-id is not a guide channel at all (`known_ids` from `EPGDatabase.get_channel_ids_lower`). On the same playlist these two rules took wrong row labels from 1,773 to 0.
- A name that answers to several guide channels is resolved by the number, not by the order the guide happens to list them in. Noise stripping turns both "BBC 2" and "BBC 3" into "bbc", so a playlist channel called "BBC 2" landed on the guide's "BBC 3" and showed its programme. The rule wave fourteen wrote down - names say whether two channels are the same, numbers say when they are not - applies to every matcher, so the guide's name indexes keep every channel that answers to a key, in the guide's order, and the matcher picks the one whose number agrees; a playlist that numbers a channel and a guide that spells it out are the same channel (`replace_word_numbers` indexes both forms). Numbers are read from the names only: a tvg-id hit is identity, not a name, and an id's digits would otherwise mask the display name's disagreement. The guide-side matching lives in `channel_identity.py` (the tvg-id variants, the guide's indexes, the matching policy) and the name vocabulary stays in `channel_names.py`, so a matcher that resolves a name takes the rule from one place. `playlist.py`'s guide-to-playlist direction applies it as a score penalty (`score = 20`), not a rejection, so it can still win.
- A purely numeric tvg-id or guide id (Dispatcharr/Xtream row numbers) is a key, not a channel number. Pass ids through `_id_number_text` before `_significant_channel_numbers` or `_extract_hbo_variant`: read as a number, tvg-id "2" sent "ESPN" to "ESPN 2" and "HBO" to "HBO 2" whenever the guide did not know the id.
- The EPG import keeps `wal_autocheckpoint=0` but runs `PRAGMA wal_checkpoint(PASSIVE)` after each batch commit. Without it the whole guide went through the WAL before the final TRUNCATE (over 1.8 GB of WAL beside a 600 MB database for a 618 MB feed); with it the WAL peaked at 44 MB and the import was no slower (99 s against 106 s).
- EPG search text is matched literally: `_like_escape` plus `ESCAPE '\'`. `strip_noise_words` still turns `_` into a space on the channel-name side, which is intended.
- Guides can define one channel id more than once with different names (that Dispatcharr feed had 390). The importer skips repeats within a source; otherwise `insert_channel` read the second name as a renumbered channel and deleted the id's programmes, history and catch-up included, on every import.
- The `channel_sources` table (channel id, sha1 of the EPG source URL) records every source that lists each channel; several sources can share an id. After a source imports with channels, `_drop_channels_missing_from` removes that source's listings for channels it no longer defines and deletes a channel (with its programmes) only when no source lists it any more. Before, retired ids stayed forever and still counted in `get_channel_ids_lower`, so a playlist channel carrying one never fell back to a current namesake for its row label. Keep the cleanup per source and per listing: a provider whose playlist fails contributes no EPG URL to the run, and a run-wide cleanup deleted all of its channels and catch-up history; a single last-writer source per channel deleted an id another, absent source still listed. A failed or empty source, or a channel no source has listed yet (written by an older build), is never dropped by that per-source pass. `channels.last_seen` (epoch of the last import that listed the channel) backs it up: after any run that imported a source, `_retire_unseen_channels` deletes channels no import has listed for 14 days, which catches a source whose URL changed (a rotated token gives it a new source key) and rows from before `channel_sources`. Programmes are pruned after 14 days anyway, so nothing worth keeping goes with them. The migration stamps existing rows with the upgrade time.
- `_xtream_timeshift_url` keeps the live URL's query string (provider tokens) and its `|Referer=...|Cookie=...` modifier tail on the archive URL and adds `http-user-agent` only when the tail has no User-Agent, read with `split_stream_modifiers` so aliases such as `UA=` count.
- Logs and the diagnostic report deliberately keep stream URLs, headers and provider credentials verbatim (recording log header, EPG debug log via the root-logger file handler in playlist.py, ffmpeg stderr). Do not re-introduce URL masking or redaction helpers there; the owner wants logs usable for troubleshooting.
- Some Xtream-style live TS servers end the HTTP response periodically. Live `.ts`/MPEG-TS handling should reopen cleanly without consuming normal reconnect-attempt budget.
- Automatic update checks should be throttled and use short metadata timeouts; interactive update checks/downloads may use longer waits. Do not schedule passive GitHub checks before the initial playlist load has yielded UI.
- Large existing EPG databases can make _ensure_db_tuned() a multi-second operation when an index is missing (observed 5.6 GB epg.db, 16M programmes, 14s index creation). Never run EPG DB tuning before the main frame is shown; keep it deferred/background or tied to actual EPG import/query work.
- Keep `_ensure_db_tuned()` index creation consistent with `EPGDatabase._create_tables()`: never recreate the redundant `(channel_id, start)` index after the database layer drops it, because rebuilding it over a multi-gigabyte EPG can saturate disk/CPU during startup and make unrelated UI actions such as search appear frozen.
- Autodetecting Xtream credentials from a URL must stay conservative: only a `*.php` endpoint with both `username` and `password` params, or an exact 3-segment / prefixed 4-segment / `timeshift` 6-segment path ending in a numeric stream id. A false positive shows the user an account that does not exist. Detection dedupes on (kind, host, username), because panels serve `get.php` and the streams themselves from different paths.
- `tests/test_source_hygiene.py::test_no_hardcoded_provider_credentials` also fires on `password=account.password`-style keyword arguments and on comments containing that text. Bind short locals (`user, pw = ...`) instead of weakening the guard.
- A favorite must never be keyed on the resolved stream URL. Xtream and Stalker mint a fresh URL on every resolve, so the favorite would be lost at the next playlist refresh, and the URL carries the account username and password, which must not be written into `iptvclient.conf`. `favorites.channel_key()` joins provider type/id, stream id, tvg-id and display name, and falls back to the name alone for plain M3U playlists (so the same channel in two categories is one favorite, deliberately).
- `Favorites` is a category *sentinel* like `All Channels`: stored and compared in English, displayed translated and with a count. That broke `_refresh_group_ui`'s old selection restore, which round-tripped `current_group` through the visible label (`FindString` + a `startswith(f"{group} (")` scan) and so could never find a sentinel in a translated UI. It now restores by index into `_group_keys`, which holds the real keys.
- A long background job with no window of its own must report its own completion. `File > Import EPG to DB` promised "will start in the background" and then never spoke again. `start_epg_import_background` now returns whether it actually started and takes `notify=`; only the hand-started import sets it, so the periodic automatic refresh stays silent instead of stealing focus. The completion box goes through `_show_or_queue_message_box`, and is shown *after* `on_highlight()` so the reloaded guide is already behind it.
- A stream URL may carry an M3U `|Key=Value` tail, and `_build_generic_catchup_url` re-attaches the channel's `|User-Agent=` to every template-style (`catchup="append"`) catch-up URL. Players parse that tail; HTTP does not - it lands in the query string. `_begin_catchup_download` therefore splits it off with `http_headers.split_stream_modifiers` and merges the result into the channel headers before probing, or the `index-<utc>-<duration>.mp4` probe always fails and the download silently falls back to the HLS playlist, which arrives at playback speed instead of line speed. `internal_player._parse_stream_modifiers` delegates to the same function so the two cannot drift.
- The header gateway hands the channel's HTTP headers (Cookie, Authorization) to whoever asks for a gateway URL, and the token in that URL goes out to every receiver on the LAN. The gateway path carries the upstream host, so the headers only go to the host the session was created for, plus any host the provider redirected it to - a request that names a stranger's host gets no credentials.
- XMLTV timestamps may legitimately be shorter than 14 digits: the spec allows trailing components to be omitted ("202609270600 +0100", "20260927"), and real feeds publish the minute-precision form. The `_XMLTV_TS_RX` regex used to require the full 14 digits, so every programme of such a feed parsed to None and the importer's `st_utc and en_utc` guard dropped the entire guide silently. `_parse_xmltv_to_utc_str` now accepts 8/10/12/14-digit forms, filling month/day with 01 and the rest with zeros like the reference XMLTV::Date parser; odd digit counts still fail. `tests/test_epg_database.py::test_xmltv_short_timestamps_parse_to_utc` pins it.
- `_open_catchup_dialog` must never run `_get_catchup_programmes` on the GUI thread: the fuzzy match (`resolve_best_channel_id`: candidate LIKE scans plus up to 20 availability probes) takes seconds on a full guide and freezes the app and NVDA with it while an EPG import saturates the disk - the documented search-path failure. It submits the lookup to `_epg_executor` and opens the dialog via `wx.CallAfter`, like View EPG, What's On Now and Schedule Recording already did; the `_catchup_dialog_open` flag prevents a double press from queueing a second dialog. `tests/test_catchup_return_and_downloads.py::test_catchup_list_lookup_runs_off_the_gui_thread` pins the delegation.
- `ChannelEPGDialog` skips malformed programme dates. Keep its selected-programme mapping aligned to the rows actually inserted, and leave an empty list unselected; otherwise descriptions and Schedule Recording target a different programme.
- CPU audit 2026-10-06 (49,556 channels, 53,615 guide channels, 2.05M programmes). The 60 s now-playing refresh cost ~12 CPU-s per minute forever: `canonicalize_name`/`strip_noise_words` regexes (~13 s per pass at 125k channels) and `strptime`+`astimezone` in `_programme_label` (~15 s). Both are now cached (`channel_names._NAME_CACHE_SIZE` bounded `lru_cache`, ~25 MB at this size; `main._local_hhmm` keyed on the UTC offset), and the timer skips while the window is in the tray (`restore_from_tray` refreshes). Keep these functions pure or the caches go wrong. `get_all_now_next` must stay on `idx_programmes_start_cover` columns only and fetch descriptions for the on-air rows by id: selecting `description` in the window query forced a table lookup for all ~212,000 rows (2.05 s -> 0.80 s). Highlighting an EPG search row ran `_find_matching_channel_for_program` (full fuzzy scan) twice on the GUI thread, 2.5 s, which NVDA reported as a freeze on End; it now uses `_program_match_index` (built once per `all_channels` identity, warmed by the EPG search worker, dropped wherever `all_channels` is replaced so it cannot pin the old list) plus an exact tvg-id fast path and a per-row memo. Word overlap scores at most 30, so it only matters when the score is still below 30. Playlist parsing (0.9 s for the 12 MB M3U) and the importer (~110 us per programme) were measured and left alone. Profile with the real `parsed_*.json` caches and `epg.db` before touching any of this.
- A `threading.Lock` that the same thread takes twice is a deadlock, not a mutex. `StreamProxy._cleanup_loop` held the proxy lock and called `_expire_gateway_sessions`, which took it again: the cleanup thread wedged for good with the lock held, and every converter, playlist and segment request blocked ten seconds after the proxy started. `StalkerPortalClient._ensure_token` held the token lock across `_portal_call`, which took it again on a 401/403: a wrong MAC or an expired trial hung the thread for good instead of raising `ProviderError`. Both locks are `RLock` now. When a lock is held across a call, that call must not take it again - use an `RLock` or restructure. A test for this must not hang: run the re-entrant call in a thread and assert an event within a few seconds.
- PowerShell 5.1 silently ignores a named argument that matches no parameter: `Get-ParentAppProcess -Id $pid` bound nothing and left the parameter at 0, so the helper read the Idle process (PID 0) instead of the app. Name a parameter to match its call sites, and never trust a "no error" that came from an argument that never bound.
- A country code that is also an ordinary word is only a code where a code is meant. "Car SOS" was tagged Canadian and then looked for a Canadian guide, because the synonyms were matched as free words. The bare codes and the word-like variants ("can", "car", "nor", "per", "ind") are matched only as a leading or parenthesised code in capitals, and the spelled-out names are still free words.
- The channel's custom headers travel in `_extra` (the app's convention for headers to expand). Anything that sends headers has to expand them: a header literally named `_extra` never reaches the provider, and the list - which can carry a secret - goes out under a name nobody asked for.
- A word is not a country tag. "car" was a strip tag, so "Car SOS" and "SOS" canonicalised to the same name and the guide of one matched the playlist of the other. The strip tags and the group synonyms both need the rule: a country code that is also an ordinary word is matched only where a code is meant - a leading or parenthesised code in capitals, or the spelled-out name.
- An EPG import never fails: every source fails on its own and the importer logs it and moves on. The number of guides that came in is what tells the caller whether the guide is up to date, so `import_epg_xml` returns it and a run that imported nothing is a failure (the box says so, and the run is not recorded as fresh, which is what suppresses the next automatic import).
- A source that cannot be fetched keeps the channels and the provider session it had, and the refresh says it failed. A playlist that is one refresh out of date is better than a playlist that disappeared because one download failed. The fallback is per source: a source that was fetched replaces its channels as before.
- The provider's JSON is untrusted input all the way down. A null row in a category or stream list is skipped like a broken number is, and a portal reply with a null "js" is a provider error, not an AttributeError the user reads as "Could not resolve stream URL".
- A provider that rejects the password has told the caller nothing about the account. The report must not add an expiry line to it: "Expires: Never" told the user their dead account never expires.
- A match rule that compares two names for equality is a dictionary lookup, not a scan. The programme matcher scored every channel in the playlist for every row the user highlighted: 491 ms on a 257,000-channel provider, on the GUI thread, and 23 seconds for one page of EPG search results. The index carries a table per equality rule, and only the weak rules (a substring, a word in common - 40 and at most 30) still need every channel, so the scan runs only when nothing matched strongly. The tie-break stays the same: the first channel wins.
- An index over the whole playlist is built when the playlist changes, not when the user asks for something. It took twelve seconds with a cold name cache, and the user paid it on the first lookup.
- Measure on the provider's own data. The 257,000-channel playlist on this machine showed the match cost (491 ms per lookup) and the index build (12.9 s) that no amount of reading the code had made obvious.
- A read-only open of a database that does not exist yet fails with "unable to open database file". That is not an error: there is no guide yet, and every view has to show an empty guide rather than a raw SQLite message.
- Say what is happening while it is happening. The categories said "No channels found." while the playlist was still loading, because a search rebuilt them; the app's own log shows three minutes and twenty seconds of it.
- Do not carry what nothing reads. Every channel's logo URL was parsed, cached and kept in memory, and the app has no channel icon: 17 MB of a 64 MB cache file and about a tenth of the memory the playlist costs.
- Write the cache off the path the user is waiting on. The parsed playlist cache is 43 MB of JSON on a big playlist and took ten seconds to write, inside the load worker, before the channel list was applied: the list appeared ten seconds late for a file nobody was waiting for.
- Start the background work after the foreground work. The match index is built over every channel in the playlist, and starting it before the channel list was applied made the apply take 10.8 s instead of 0.8 s: both run in threads and fight over the interpreter lock.
- Run the app. Starting it on the user's own playlist and watching it settle found in minutes what reading the code did not: the channel list arriving twenty-four seconds late, the categories saying the wrong thing, and the guide that could not be opened.
- Say how long the phases take. The playlist load's phases were nowhere in the log, so a slow load could not be told apart from a slow provider; they are in the log now.
- The numbers in a channel name are the channel. The canonical name drops a standalone digit as a noise word, so "BBC 1" and "BBC 2" looked the same and the guide's programme landed on the wrong channel; the number helpers live in `channel_names.py` now, and every matcher compares them.
- Test the name machinery against a real corpus. The 31,645 channels of the iptv-org catalogue showed 510 families whose members the canonical name merges - something no amount of reading the name code had made obvious.
- Read every file the way a user's file arrives. A playlist that starts with a UTF-8 mark was read as if the mark were part of the first line: the playlist opened with a channel that cannot play. The download path stripped the mark and the file paths did not; the file paths read "utf-8-sig" now, and the parser strips the mark as well, so a mark cannot reach the channels from any path - and a parser change like that bumps the parsed-playlist cache version.
