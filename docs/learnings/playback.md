# Playback (libVLC, buffering, subtitles)

Moved here from `agents.md` on 2026-10-22, verbatim. `agents.md`
points at this file; read it before changing the code it names and
grep it for the module, symbol or error you are about to touch.

- `sitecustomize.py` must remain a shim. The internal player implementation belongs in `internal_player.py` only.
- Live stream VLC options should allow late-frame dropping/skipping so playback can catch up to real time. Catch-up/VOD can use stricter frame options.
- Internal-player caching honors the configured duration across access types, without bitrate floors, extra padding or forced demux read-ahead. Retry increases apply only to the current stream; changing channels resets the initial duration. Xtream-style refresh should wait for sustained buffering instead of restarting on tiny blips.
- VLC can start muted with dummy/hidden interfaces. `_schedule_volume_apply()` explicitly unmutes before applying volume.
- Auto-update is for packaged Windows builds. The helper script uses PowerShell parameter names (`-ParentPid`, `-InstallDir`, `-StagingDir`, `-BackupDir`, `-ExeName`), not GNU-style flags.
- libVLC resets the audio track every time the media object is recreated (each reconnect/xtream refresh), so `audio_set_track()` must be re-applied by matching the chosen track name once playback resumes; the built-in player stores `_wanted_audio_track_name` and re-applies it in `_on_timer`.
- libVLC has not published `audio_get_track_description()` by the time the player first reports `Playing`, so a preferred-track match cannot be a one-shot check: `_maybe_apply_preferred_audio_track` retries on the 500 ms status timer for ~10 s (`_max_audio_preference_attempts`) before giving up. Applying the preference sets `_wanted_audio_track_name`, which is what the existing reconnect path re-applies, and a track the user picked by hand always wins.
- Audio-description track names are not standardized and are not always English ("Audiodeskription", "Hoerfilm", "AD", "DVS"). `audio_track_matches` therefore matches on whole word tokens, with a substring fallback only for keywords of 6+ characters. Without the word rule, "AD" selects the Radio track; without the substring fallback, "audio description" misses "Audiodescription-Ton".
- libVLC's `stop()`, `player.release()` and `instance.release()` are synchronous: they wait for the demuxer and the HTTP access thread to unwind. Closing the built-in player ran all of them on the GUI thread, so with the machine busy - an EPG import saturating disk and network is the reported case - the message pump stopped and the whole app went unresponsive, greyed out to Windows and silent to NVDA. `_exit_player` now hides the frame, tells the app it has closed, and runs `_release_vlc` on a worker thread; `_finish_destroy` destroys the wx frame afterwards, because VLC must let go of the video panel before wx destroys it. `Destroy()` and a non-vetoable `_on_close` join that worker (bounded by `_VLC_TEARDOWN_JOIN_SECONDS`) before letting the destruction through. `_release_vlc` is idempotent, so the two paths cannot double-release.
- Main-window shortcut ownership is deliberate and regression-tested: `Ctrl+Shift+J` exclusively shows the already-loaded built-in player, while `Ctrl+Up`/`Ctrl+Down` control volume. Do not restore the dead legacy `Ctrl+Shift+J`/`Ctrl+Shift+K` volume bindings; the former silently stole the documented Show Player shortcut.
- A restart that never worked is not a completed update: `Complete-SuccessfulUpdate` takes `-Restarted` and, when it is false, says the update is installed but the app could not be started (`restart` message) instead of "Update complete", and records nothing for the app to read.
- Brief live audio cut-outs with no "Reconnecting" in the log are libVLC rebuffers. Enable VLC file logging (`--verbose=2 --file-logging`) and look for `ES_OUT_SET_(GROUP_)PCR is called too late (pts_delay increased to N ms)` followed by `ES_OUT_RESET_PCR`: the data arrived later than the network cache allows. Before touching the player, compare the stream's arrival on this PC with a read from the restreamer's own localhost; if both show the same gaps, the source is upstream. On 2026-09-29 the Dispatcharr/SceneTime KOMO gaps (5-13 s, every ~6 s) were a restreamer pacing bug, and a 5 s buffer rebuffered exactly as often as 2 s in a side-by-side run, so the 2 s default stays. Measure buffer changes with two players side by side, never one after the other: provider conditions change minute to minute.
- The position-based stall check has a startup grace of `_av_startup_grace_seconds + base_buffer_seconds`. libVLC reports Playing while its clock sits still filling the cache, so without the grace a reconnect that raised the buffer was judged stalled 4 s later and each retry raised it again.
- libVLC transport calls (`stop`, `set_media`, `play`, `pause`) go through `InternalPlayerFrame._vlc_call`, a one-thread executor, never the GUI thread. `player.stop()` blocks until the old stream unwinds and that grows with the cache: measured 0.4-0.9 s per channel change at 6 s, 30 ms at 1 s, all of it lag after Enter. One thread keeps stop before the next open, which one-stream providers need. `_on_timer` skips while `_vlc_switch` is pending (the old stream's Stopped is not a dropout); `_release_vlc` shuts the executor down first.
- The buffer is start-up time: libVLC withholds sound until `network-caching` is filled. Warm Dispatcharr channel, measured: 0.8 s to sound at 1 s (VLC's own default), ~2.5 s at 2 s, 7-12 s at 6 s. Default is 2 s again (2026-10-06, the user's choice after 6 s made connecting feel slow). A cold Dispatcharr channel adds 4-10 s of server start-up the client cannot shorten.
- Dispatcharr answers a reconnect to a channel it is still tearing down (or restarting) with `503 {"error": "Channel is stopping, retry shortly"}` and `Retry-After: 1`, and libVLC reports that as Ended about 0.5 s after opening. The player used to burn its whole budget in ~8 s (4 tries, 0.4 s apart plus the 2 s cooldown) and say "Stream lost" while the server was seconds from ready; the user's log had 40 give-ups in a week, each a burst of 503s in the server log. Reconnects now back off 0.4, 2, 4, 8, 8, 8 s (`_reconnect_delay_ms`, 6 attempts, ~30 s). A connection that never reached Playing is a failed open, not a TS rollover, so `_restart_expected_xtream_live` refuses it and it goes through that budget instead of six instant refreshes. `play(_retry=True)` must keep `_detected_content_ts`: clearing it on every play moved Dispatcharr's extensionless `/live/U/P/ID` streams out of the rollover path after their first refresh. Diagnose with the app log (`%APPDATA%\AccessibleIPTVClient\logs\iptvclient_epg_debug.log`, grep `internal_player`) beside `docker logs dispatcharr | grep "GET 503 /live/"`; the server is UTC, the client local time.
- Dispatcharr fails a channel over to its backup streams on the server, and while it does it sends **nothing**: no HTTP response at all until the channel is ready or it gives up (its "Channel Initialization Timeout", `channel_init_grace_period`). libVLC stays in `Opening` for as long as a server is silent (measured: 40 s against a socket that never answers), and the startup timeout used to run only in `Buffering`, so a dead channel was never timed out by the player. The startup timeout (`_first_start_buffer_timeout_seconds`, 25 s) now covers NothingSpecial/Opening/Buffering before the first Playing, and must stay longer than the server's initialization timeout (tv.serrebiradio.com: 20 s since 2026-10-07): a client that leaves mid-failover makes Dispatcharr tear the channel down, and the next connection starts over at the first, dead stream (Dispatcharr #1455, #1756, #1380). A channel that has not played once `_first_play_deadline_seconds` (30 s) after the user chose it is reported as lost at the next retry instead of spending the whole 6-attempt budget (minutes). "no media received" does not raise the buffer: nothing arrived, a bigger cache only adds start-up time. Server side, Dispatcharr 0.31.0 also has #1672 (a switch keeps the dead stream's health state and skips the next good backup); tv.serrebiradio.com patches it at container start with `/data/patch-failover-health.py`.
- The shared subtitle manager must be cleared on every playback transition, and `SubtitleSessionController` is how. The built-in player cleared only its own cue list, so "Read current subtitle" and "Review recent subtitles" answered with the last line of the channel the user had just left; the controller's `activate_session`/`cancel_session` existed but nothing called them. `_launch_stream` activates a session before `frame.play(...)` and `_on_internal_player_closed` cancels it. The manager also drops a speech that was queued before the clear (an epoch counter), because the speech runs on the UI thread and can still be pending when the source changes.
- Nothing slow may run inside the scheduler tick. Starting a recording resolves the stream URL, classifies the media and probes its audio tracks, which takes seconds; it used to run inline, so the tick could not run while it did and a recording that came due started late. The job is claimed under the lock first and the blocking work goes to a worker, so a second tick cannot start it twice and a cancel during the start is still caught. The hourly series scan was moved off the tick for the same reason.
- One reader at a time on a pipe. The MPV transport had no read lock while the reader thread and a request's inline pump both read it: two readers split a message, the JSON failed to parse and the message was lost. A check that gates a feature must not gate it on a slow peer either - the MPV version check used to drop the whole subtitle session when a cold mpv answered late.
- The player has to know the media type. The A/V watchdog restarts the stream when either track stops progressing, and a radio station's cover art - which decodes a couple of frames and then freezes - armed the video watchdog, so the player reconnected every ten seconds while the audio played perfectly well. The app knows the source is audio-only (`media_type.channel_media_from_metadata`); the player has to be told, because `video_visible` says nothing about the media.
- A value read from the user's config is untrusted, so it is checked where it is read, not only where the app writes it. A hand-edited shortcut must not install a bare main-window key (it would swallow ordinary typing in the search box) or take F1 (the help key); `shortcuts.effective()` applies the same rules as `shortcuts.set_shortcut()`.
- The application-owned MPV belongs to the app. Launching any other player closes it, and a launch that was superseded while its handshake was running installs nothing and hands off nothing: the handshake takes seconds, and the old channel must not start over the new one.
- The automatic subtitle speech is checked when the cue is spoken, not only when it arrives: a cue queued while the speech was on is not spoken after the user turns it off. An explicit "read this subtitle" always speaks.
- The application voice speaks asynchronously, so a caption line outlives the channel it belongs to. The voice is purged whenever the subtitle session changes - a new stream, or the player closing.
- A timer that talks to libVLC is stopped when the player is torn down. The cue timer asked a released player for the subtitle position: a native crash, not an exception Python can catch.
- A track's name drifts between connections; its slot usually does not. A chosen audio track is re-applied by name first and by slot when the name no longer matches, and the label follows the name the provider now uses.
- The machine's own leftovers are evidence: the temp folders, the crash dumps, the firewall rules and the app's log say what the installed build did, which the source alone does not.
- Anything the app opens for a local client to connect to belongs to one session. The external-player MPV pipe carried a fixed, machine-wide name, so any process on the box could read the session's media title and send it commands; it is built per session now, like the subtitle adapter's. A pipe name is an address, and an address everybody can guess is a door.
- Age pruning is for a live stream only. The relay kept dropping chunks older than two seconds even after ffmpeg had exited, so a player a little behind when the recording ended lost up to two seconds of its tail; `close()` also marked the stream finished while the pipe could still hold bytes. Stop pruning when closing, give the pump a bounded moment to reach EOF, and only then force the end.
- Subtitle follow-up (2026-10-23): a producer needs a session-bound sink, not only a manager pointer. Register adapters with their token and retire late worker results. Current-text MPV snapshots are assembled inside a private Lua helper during `register_idle`; `format_json` returns two values, so assign the result before passing it to `commandv`. The IPC reader is the only transport consumer; requests wait on matched events. Keep the version advisory and process/setup work off the GUI thread. Route built-in automatic and manual speech through the configured backend. SAPI token IDs survive loss and approved fallback; successful async synthesis is not proof of physical endpoint delivery. See `docs/subtitle-speech-integration.md` for limits and the Windows acceptance matrix.
- Subtitle follow-up after v1.150.40: a same-file reload may reuse a previously verified SPU ID. Retain that proof only for the same canonical file URI and identical parsed cue text/timings; changed contents, an unknown prior binding, track disappearance or an intervening generation must not be promoted. The file-size cap must be enforced by a bounded read before allocation, not after read_bytes(). Capability reports translate display labels, never internal player keys.
- ASS/SSA speech extracts Events Dialogue using the declared Format (Text last), keeping words and timestamps while suppressing overrides and persistent drawing mode. It is not visual rendering or simultaneous-track composition. Private SAPI rate uses -10..10 and takes effect at the next Speak stream; do not change programme speed or screen-reader settings. The generated local HTTP/MPV test exercises live SRT and ASS through the production Lua helper, adapter, bound session and shared manager with one upstream GET. It does not prove built-in live decoding or native endpoint delivery; see `docs/subtitle-followup-15040.md`.
