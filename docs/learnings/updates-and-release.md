# Updates, release and translations

Moved here from `agents.md` on 2026-10-22, verbatim. `agents.md`
points at this file; read it before changing the code it names and
grep it for the module, symbol or error you are about to touch.

- Startup smoke tests of a portable build can write `iptvclient.conf` beside the executable even with fresh `APPDATA` and a scratch working directory. Test a copied bundle, or wait until release archives are sealed; never run the release-tree executable between config validation and zipping. Verify the final zip contains no config.
- Windows installer builds use Inno Setup with a `.windows-installed` marker in Program Files. Installed/runtime mutable state belongs under `%APPDATA%\AccessibleIPTVClient`; Program Files should contain only application binaries and bundled assets, and installed auto-updates should use the signed setup EXE rather than replacing Program Files directly.
- Authenticode verification must use Windows PowerShell 5.1 with a clean environment because PowerShell Core module paths can break `Get-AuthenticodeSignature` from Python subprocesses.
- Installed updates keep `iptvclient.conf` in `%APPDATA%\AccessibleIPTVClient`; portable zip updates preserve or migrate `iptvclient.conf` beside `IPTVClient.exe`. This is different from bundling a repo config file in a release, which must not happen.
- PyInstaller hidden imports for chardet mypyc modules are required for clean builds in the current environment.
- PyInstaller `--noconsole` / `console=False` builds set `sys.stderr` (and `sys.stdout`) to `None`. `http.server.BaseHTTPRequestHandler.log_message` writes directly to `sys.stderr`, so its default implementation raises `AttributeError: 'NoneType' object has no attribute 'write'` on the FIRST line of every response (send_response → log_request → log_message). The exception propagates, the handler thread dies, and clients see an empty reply / `curl: (52) Empty reply from server`. `StreamProxyHandler` MUST override both `log_message` and `log_error` to route through the project's `LOG` (or swallow) so the bundled exe can actually serve responses. Source-tree runs hide this bug because a console stderr exists.
- `tests/test_i18n.py` requires **every** catalogue in `i18n.SHIPPED_CATALOGS` to be fully translated, not just Hungarian. After adding user-facing strings and running `python tools/i18n_tools.py all`, fill the new `msgstr` in all thirteen `locale/<code>/LC_MESSAGES/iptvclient.po` files before compiling, or the i18n tests will fail.
- Do not patch update manifest JSON with PowerShell `Set-Content`; it can write a UTF-8 BOM, and same-name GitHub release asset replacements may be served from cache for a while. Prefer regenerating manifests through `tools/release.py` or explicitly writing UTF-8 without BOM.
- Account/subscription reports must stay plural-free and password-free: phrase day counts as separate `Days remaining` / `Days since expiry` labels rather than "in N days" (the app has no ngettext catalogues, and `i18n_tools`' PO writer does not emit plural forms), and never render a password into text that gets read aloud, copied to the clipboard, or pasted into an issue.
- `build.bat release` prepends a readable version/date entry to `CHANGELOG.md` from the generated release notes before the version commit and tag. Keep `CHANGELOG.md` staged with `app_meta.py`; historical entries were reconstructed from the Forgejo mirror.
- Release notes list every non-merge commit subject since the last tag, except commits that change only `locale/*/LC_MESSAGES/release_notes.{po,mo,pot}` and commits whose body has a `Changelog: skip` footer (`tools/release.py::is_changelog_exempt`, issue #27). Translating What's New must never itself become a What's New bullet, or every translation adds a new untranslated entry. Commit What's New translations alone, and use the footer for other maintenance that users should not see (for example a CHANGELOG.md cleanup).
- Committed `locale/**/*.po` files are LF-only. When filling translations with a helper script, open files with `newline="\n"` (or in binary mode) — the default Windows text-mode `open(..., "w")` rewrites every line as CRLF and churns the whole file. Re-running `python tools/i18n_tools.py update` re-normalizes to LF and preserves existing `msgstr`s.
- A detached FFmpeg finalizer can keep the bundled `ffmpeg.exe` locked after the app has exited. Before an update replaces the installed or portable app directory, `update_helper.ps1` must enumerate both the app process and `ffmpeg`, then stop only images whose `MainModule.FileName` is inside `$InstallDir`. Do not kill arbitrary FFmpeg processes elsewhere on the computer.
- The Windows installer's `[InstallDelete] Type: filesandordirs; Name: "{app}\_internal"` wipes the PyInstaller runtime before the new files land, so for the length of the install the installed exe cannot start at all: it dies with "Failed to load Python DLL ...\_internal\python314.dll". The app is already closed by then, so the obvious user reaction - clicking the shortcut again - lands exactly in that window. `_warn_update_is_installing()` says so *before* the helper is launched (the helper only waits 30 seconds for our PID to exit), and `updater.write_update_pending()` drops a marker in the per-user config directory - not the install directory, which is what gets replaced - so `_report_finished_update()` can report on the next start whether the update landed.
- Filling `.po` translations programmatically: parse the PO blocks yourself and write with `newline=""` so the LF-only files stay LF (Windows text mode churns every line to CRLF). Split long msgstrs into `msgstr "..."` + continuation `"..."` lines, escaping `\n` as literal backslash-n. `tools/i18n_tools.py update` re-normalizes to LF afterwards, so a quick `update` + `compile` also heals a CRLF accident.
- Hungarian review issues from @htibcsike can arrive in rounds inside one issue: an interim comment supersedes the original body, then the body itself is edited last with a closing comment saying to use it. Compare the issue's `updatedAt` against the comment timestamps and treat the *last-edited body* as authoritative, not the first text or the interim comments. When such a review claims an English-source/behaviour mismatch (issue #20, recording-log bullet), verify the claim against the actual code path before touching `docs/help/en.md`; `en.md` is the reference `hu.md` mirrors, so fix the English first and keep both in step.
- Release notes are localized through gettext, never by translating `CHANGELOG.md` or mirroring it per language (issue #25). `release_notes.py` owns the section labels (`SECTIONS`: Breaking changes, Features, Accessibility, Bug fixes, Documentation, Other changes) and "No notable changes." as ordinary `iptvclient` strings, which must stay fully translated. Individual bullets live in the separate `release_notes` domain (`locale/release_notes.pot`, `locale/<lang>/LC_MESSAGES/release_notes.{po,mo}`), which is deliberately exempt from `test_shipped_catalogue_is_fully_translated`: translators fill it in after a release and untranslated bullets fall back to English. `i18n_tools.py notes` (also run by `all` and by `release.py sync_translations()` right after the CHANGELOG entry is written) extracts bullets from the newest three `## v` entries only (`RELEASE_WINDOW`/`NOTES_WINDOW`, agreed with @htibcsike: current plus previous two) and rewrites every language's `release_notes.po`, keeping translations of bullets still in the window and retiring the rest. `release.py` now writes CHANGELOG entries with `### <label>` groups and cleaned, de-duplicated bullets, and the GitHub body/manifest summary uses the same English labels; `ChangelogDialog` shows `release_notes.localize_changelog()` (translated intro replaces the maintainer preamble) and the update prompt uses `localize_notes(clean=True)` for older bodies with `fix:`-style prefixes. The update prompt can only translate labels for a new release, because the running app's catalogue predates its bullets.
- `classify_commit()` must never substring-search the commit **body**. An `i18n(hu)` commit whose body honestly mentioned the section label "Breaking changes" was matched by the old `"breaking change" in text` check, classified Breaking, and released as v2.0.0 within minutes (0 downloads; deleted, main rewound past `chore(release): v2.0.0`, re-released as v1.136.1). Breaking is now subject `type!:` or a real `BREAKING CHANGE:`/`Breaking changes:` footer only; `fix`/`feature`/`bug` matches read the subject alone. Regression tests pin this in `tests/test_release.py`. Never write a section label verbatim in a commit body on this repo until that rule is second nature.
- An Authenticode pin that travels with the release proves nothing: whoever can publish a release can sign it with their own certificate and declare that certificate in the manifest next to the file. The pin has to come from outside the release - the environment override, the certificate the running application was signed with, or `updater.TRUSTED_SIGNING_THUMBPRINTS`. The manifest's own value is a last resort for a source run with no signature, and that case is logged. A certificate rotation is delivered by an update signed with the old certificate that already carries the new pin.
- **The status window used to be created invisible.** `updater.popen_hidden` passes a STARTUPINFO with `wShowWindow = SW_HIDE`, and Windows applies that to the *first top-level window the process shows*, not just to a console - so the helper's WinForms window existed, with the right title, but `IsWindowVisible` was false until something forced it to the foreground. That only happened after the app had exited, which is exactly the reported "the update window disappears at Preparing the update": for the whole of that step there was nothing on screen. `launch_update_helper` now passes `_no_show_startupinfo()` (CREATE_NO_WINDOW still keeps the console away) and `Show-UpdateStatus` calls `ShowWindow(SW_SHOWNORMAL)` itself. Never launch the helper through plain `popen_hidden` again.
- Inno Setup must not close applications itself (`CloseApplications=no`, issue #31). With the default `yes`, Restart Manager reported the update helper's own Windows PowerShell as "an application using one of our files", could not shut it down - it is the process driving Setup - and the `/SUPPRESSMSGBOXES` default for that prompt is Abort, so every install rolled back with exit code 5. `CloseApplications=force` would be worse: it would terminate the helper mid-update. The updater already closes the app and kills anything left running from the install directory.
- `tools/smoke_update_window.py` drives the real window through both halves of a real update (download with Cancel, then the hand-over to the install) and checks what pytest cannot see: that it appears at all, that the title follows every step, that it survives the app closing, and that it refuses to close. Run it after touching `update_helper.ps1` or the session protocol. Everything it starts besides that window is windowless on purpose - a console stand-in for the app stole focus from whoever was running it.
- `Write-UpdateSuccess` must run **before** `Start-AppAfterUpdate`, not after. The restarted app reports the update about 50 ms after it shows its window, while the restart check deliberately blocks for five seconds proving the new process survived; a result written after that race was lost, `read_update_result()` returned None, and the new version opened its own "successfully updated" box on top of the update's own window - the box this window exists to replace.
- Anything that gives up on a live helper must stop it (`_stop_update_helper`). Its window has no close button and cancels `FormClosing` by design, and it waits for an instruction that is never coming, so an abandoned helper leaves an always-on-top window the user cannot get rid of without Task Manager. For the same reason `_discard_update_download` takes the helper handle from its caller: `_abort_update_window` ends the flow on the GUI thread, which clears `self._update_helper`, and the folder being deleted is the one holding the running `update_helper.ps1` and the message it is about to show.
- v1.147.0/1 could not start (0xC0000409; access violation from source): `app_tts.py`'s hand-written ctypes IDispatch called `GetIDsOfNames` without `riid`, declared VARIANT as 16 bytes (24 on x64), used the nonexistent `wintypes.GUID`, and gave AddRef/Release no `this`. `IPTVClient.__init__` calls `set_volume` at startup, so every Windows user crashed. Constructing `AppTtsBackend` alone never reaches Invoke, which is why mocked tests passed; `tests/test_app_tts.py::test_real_sapi_calls_do_not_crash` makes real SAPI calls. Object properties (`AudioOutput`) need `DISPATCH_PROPERTYPUTREF`. The update helper used to report `Update complete` after both restarts crashed, via the Explorer fallback; a launch that ran and died now returns failure, and Explorer is only tried when `Start-Process` itself failed.
- The `GITHUB_TOKEN` in the environment is the user's own GitHub credential, and the release manifest travels unsigned, so the token must only go to GitHub hosts (`github.com`, `*.github.com`, `*.githubusercontent.com`). `updater._build_request` checks the host now; the asset downloads it names can point anywhere.
- The update helper may only kill the process that was the app. The app can exit and Windows can hand its PID to something else while the helper waits, so `Get-ParentAppProcess` compares the process's start time with the helper's own and refuses a process that started later.
- An import lock belongs to the import that holds it. The age was a fallback for a lock whose owner cannot be checked; it must never take a live import's lock, however long that import runs, and a release must only remove the lock this process holds.
- urllib copies a request's headers into the redirected request. A credential that may only go to one host has to be dropped when the redirect leaves it: the updater's GitHub token now goes through its own redirect handler.
- A release verifies what it is about to publish, and the check comes before the commit, the push and the release. The cloud workflow published the release first and checked the signature afterwards, and a published release cannot be taken back. The installer carries the same certificate the updater pins, or the release stops.
