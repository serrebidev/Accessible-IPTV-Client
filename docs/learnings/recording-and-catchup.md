# Recording and catch-up

Moved here from `agents.md` on 2026-10-22, verbatim. `agents.md`
points at this file; read it before changing the code it names and
grep it for the module, symbol or error you are about to touch.

- Expanded HTTP(S) `catchup-source` templates are complete archive URLs, even with `catchup="append"`. Only relative templates are appended to the live URL; keep offset/token expansion and user-agent modifiers in the shared builder. `tests/test_catchup_url.py` covers both schemes and modes.
- Catch-up URLs come in two styles. Path style (`catchup="default"`, `catchup-source="/1234"`) rebuilds `<source>/<stream-id>/<start>/<duration>/`. Template style (`catchup="append"`, e.g. teleelevidenie.com's `catchup-source="?utc=${start}&lutc=${timestamp}"`) is a placeholder template appended to the channel's live URL with real epoch values; `_expand_catchup_template` in main.py handles both and must be extended there for new providers. Treating a template as a static base path produces 403s.
- Teleelevidenie's current dynamic M3U can omit `catchup`/`catchup-source` and expose archive-capable channels only as `timeshift="N"` (observed `N=3`). For Teleelevidenie hosts, treat a positive `timeshift` as an implicit `?utc=${start}&lutc=${timestamp}` append template and use it as the archive-day window; this works for both HLS and TS live URLs. Do not generalize this URL inference to unknown hosts because `timeshift` alone does not define an archive URL scheme.
- Teleelevidenie enforces one account-wide media connection. `single_stream_provider_key()` recognizes only its hosts; pass that key to `RecordingManager.start()` so manual, scheduled, and catch-up recordings cannot overlap, and reject a new player/catch-up operation while the recording owns the provider slot. Audio/direct-file probes are media requests too, so gate them before starting background work.
- FFmpeg 8.x on Windows can treat finite MPEG-TS HTTP fixture responses as connection resets even with Content-Length. For recorder/DVR end-to-end tests, prefer explicit BaseHTTPRequestHandler live-style fixtures that repeat a small MPEG-TS file, catch BrokenPipeError/ConnectionResetError/OSError, and stop FFmpeg with an explicit recording duration.
- Stopping a recording must never kill FFmpeg on a fixed timer. An MP4 written with `-movflags +faststart` finalizes by writing the moov atom and then rewriting the whole file to move it in front of the media data, so the cost scales with the capture: a few seconds on an internal SSD, minutes on the external/USB/network drives recordings usually live on. The old `_graceful_stop` sent `q`, waited 8 seconds, then called `proc.terminate()` (an unconditional `TerminateProcess` on Windows), which killed FFmpeg after it had rewritten the mdat header but before the moov atom reached disk. The result is a file that is `ftyp` + one enormous `mdat` and nothing else — "moov atom not found", unplayable, with the whole recording stranded inside it. The signature is diagnostic: a capture killed *mid-recording* still has FFmpeg's 8-byte `free` placeholder between `ftyp` and `mdat`, while one killed *during finalization* does not, because `mov_write_trailer` overwrites that placeholder with the 64-bit `mdat` header first. `recorder.finalize_timeout_seconds()` now derives the budget from the output size.
- MP4 cannot carry the DVB teletext/subtitle or data streams that IPTV transport streams routinely include. `provider_mp4` used `-map 0` with `-c:s copy`, so on any channel carrying teletext FFmpeg aborted at header write ("Could not find tag for codec ... not currently supported in container") and left a 0-byte recording. The MP4 presets map `0:v?`/`0:a?` with `-dn -sn`; `provider_mkv` is the preset that keeps everything.
- Application shutdown stops recordings with `stop_all(wait=True, detach=True)`: FFmpeg is asked to quit and then left running. It is a separate process and finishes the container on its own, so the window closes immediately instead of blocking for the full finalize budget, and a long MP4 is not truncated. FFmpeg's stderr therefore goes straight to its log file rather than through a pipe we drain, so the log survives the app exiting.
- Recording logs live in `<recordings dir>/logs/<recording>.log`. New live recordings use one `time=` progress update per second so `recording_problem_times()` can pair each warning or error with the nearest preceding media timestamp; older logs fall back to elapsed wall-clock time from `Output #`. Logs deliberately retain stream URLs, headers, and provider credentials verbatim for troubleshooting. Do not mask or redact them.
- Every recording log ends with a `# ===== Recording summary =====` block that `RecordingManager._append_log_summary` writes once ffmpeg has exited: planned length (the `duration`, or a scheduled job's `planned_stop_ts` metadata), recorded length (the final `time=` line), file size, how it ended, and problems grouped by kind (numbers folded, so `Will reconnect at 100` and `at 900` are one kind), split into *while opening the stream* (before the `Output #` line: ffmpeg probing a stream joined mid-GOP, usually harmless) and *during the recording*, with times since the output opened. Those times need `-loglevel level+datetime+info`; the `datetime` flag is ffmpeg 7+, and an older ffmpeg refuses to start at all when given it, so `ffmpeg_supports_log_datetime()` asks once per ffmpeg path. Parse log lines with `recorder.parse_log_line` only: decoder messages look like `[h264 @ 0000...] [error] ...`, and the old `^\[error\]` check counted none of them, so a user's log with nine h264 errors reported zero. Summary lines start with `#` so they are never counted as problems when the log is read again.
- Automatic shutdown after recording is gated on `_recorded_since_shutdown_armed`, not just on "nothing is recording". Otherwise switching the option on during an idle evening powers the machine off immediately. Arming while something is already running or queued adopts that work; arming with nothing running waits for the next recording to start. It also waits for scheduled jobs, disarms itself once used or canceled, and its countdown dialog is created with no parent, because the main window is usually minimized to the tray by then and a dialog owned by a hidden window never appears.
- Every `wx.MessageBox` in `main.py` must go through the module-level `message_box()` wrapper. The "second box inside the first box's message loop leaves the main window permanently disabled" bug is only avoided if the deferral guard knows a box is up, and it cannot know that for boxes opened with a bare `wx.MessageBox` (which is how `_stop_recording_for_channel` reopened the bug after the first fix). `message_box()` keeps an app-wide depth and fires `set_modal_box_closed_hook()` when the last box closes, which is what drains the queued notifications.
- Some catch-up providers (teleelevidenie observed) close the HTTP connection part-way through a direct `index-<utc>-<duration>.mp4` file. FFmpeg treats the truncated read as normal EOF and exits 0, so a 30-minute download can end at 18:26 and be reported as complete. `recorder.py` captures the last `time=` stats line as `media_written_seconds` on finish, and main.py's truncation check (`_catchup_download_is_truncated`, default 10% shortfall tolerance) compares it against the requested window; short-but-clean downloads are deleted and re-queued through the existing catch-up retry flow (the `.part` rename has already happened by then, so delete the final file only when a retry was actually scheduled), and an exhausted budget gets an honest "Download ended early" box instead of "complete".
- Catch-up downloads apply the configured pre/post schedule-padding minutes through `_padded_catchup_window()`, unlike the old programme-exact window. The direct-file probe tries the padded window first and falls back to the programme-exact file, because some providers store only exact-programme MP4s. Availability/on-air checks must stay on the exact programme window: resolving availability from the padded window would misclassify a just-finished programme as still on air.
- One copy per user (`single_instance.py`, named mutex `Local\AccessibleIPTVClient-single-instance`, flock elsewhere). Two copies share the config, EPG DB, log and DVR schedule with nothing coordinating them: with minimize-to-tray on, Alt+F4 only hides the app, so reopening it started a second copy, both schedulers started the same Teleelevidenie recording seconds apart, the second got 403 (ffmpeg rc 3436169992) and the provider then dropped the first (rc=1). Signs in a user's log: `iptvclient.conf.tmp` "used by another process", "EPG import waiting for lock", a recording start with no "Recording audio tracks" line (its probe got 403). A second launch writes `show_request` in the user config dir and exits with `HANDED_OVER_EXIT_CODE` (12) once the running copy's 1 s timer (`watch_for_show_requests`) consumes it and calls `bring_to_front`; if the other copy exits meanwhile it runs after all. `update_helper.ps1` treats restart exit code 12 as success. `_report_finished_update` forces the foreground before its box, because that code ships in the *new* version and so fixes the unread "Update Complete" at once, unlike helper fixes.
- Every deliberate exit sets `IPTVClient._exit_requested` through one `request_exit()`, which the File > Exit item, Ctrl+Q (accelerator id 4004), the Linux button-menu Exit and the tray icon's Exit all use. With "Minimize to System Tray" on, `on_close` vetoes a plain `Close()` and hides the window, so `lambda evt: self.Close()` on those menu items made File > Exit look like it had quit while the app kept running and its scheduled recordings kept waiting - and the help promises "To quit the program completely, use File > Exit (Ctrl+Q)". `_exit_requested` must stay separate from `_exit_forced`, which deliberately skips the scheduled-recording and download confirmations; `request_exit` keeps that warning gate, and both cancel paths on the gate reset `_exit_requested` to False. `tests/test_accessibility_controls.py` pins both directions (an explicit Exit must not hide, the close button still must).
- Catch-up lookup worker or executor failures must clear `_catchup_dialog_open` and report an error on the GUI thread, or later attempts silently do nothing.
- A stream-type probe that leaves a restreamer still holds the provider connection behind it for a moment: Dispatcharr keeps the channel for `channel_shutdown_delay` (was 30 s on tv.serrebiradio.com, set to 1 s 2026-10-08), and a full provider makes Dispatcharr silently skip to the next stream with room. Sky Mix took 50 s because CBC/Saisons probes held both SceneTime slots, so the tune landed on dead free backups and a 60 s failover cooldown. Every probe close (finished or preempted) calls `catchup_direct.note_media_released(url)`, and the built-in player's open waits `media_settle_remaining` (at most `_MEDIA_SESSION_SETTLE_SECONDS`) for that host. Record it in `_terminate_media_probe` too: the session that preempts the probe opens before the worker thread's `finally` runs.
- Catch-up direct-file windows (padded, then programme-exact) go to `catchup_direct.direct_download_url` in one call, and every window is probed at each redirect hop before the next hop. Probing them one call at a time let the padded window's miss walk on to teleelevidenie's `timeshift_abs-*.ts`, which holds the account's one connection, so the exact `index-<utc>-<len>.mp4` and then ffmpeg got 403 (v1.149.2, "Ojciec Mateusz" on TVP 1).
- Teleelevidenie's archive HTTPS server sent only its leaf certificate on 2026-10-10 (issuer Let's Encrypt YR2). Windows PCs without that intermediate cached fail direct MP4 discovery with `CERTIFICATE_VERIFY_FAILED: unable to get local issuer certificate`, then fall back to a timeshift URL that can return 403. Catch-up probes use an explicit `truststore.SSLContext` on Windows so native chain building retrieves missing issuers while preserving certificate and hostname validation; never disable TLS verification. Keep its Windows requirement and PyInstaller hidden imports together. `tests/test_catchup_tls.py` reproduces the leaf-only chain with a local issuer server and checks rejection of wrong hostnames and untrusted roots.
- Application shutdown gives ffmpeg the same finalize budget as any other stop. `RecordingManager._stop_for_exit` used a flat `DETACH_WAIT_SECONDS` (5 s) while the normal path used `finalize_timeout_seconds`, so quitting during a multi-gigabyte faststart MP4 killed ffmpeg while it was still rewriting the file: `ftyp` + one enormous `mdat` and no moov atom, unplayable, with the whole capture stranded inside. The shutdown budget is now `max(DETACH_WAIT_SECONDS, finalize_timeout_seconds(rec.fmt, rec.written_path))`, and the terminate/kill escalation still guarantees no orphan ffmpeg holding a provider's one stream slot.
- A JSON or timestamp out of a file the app wrote is still untrusted input. The DVR schedule was read with a bare `float(job.get("stop_ts") or 0)` outside any `try`, so a hand-edited value raised out of the scheduler's constructor and the app did not start; `dvr._number` coerces every stored number now, and the same is true of the settings backup's parser errors.
- A canceled DVR job stays canceled, on every path. Starting a recording takes seconds (it resolves the URL and probes the audio tracks), and a cancel in that window leaves the job "recording" until the start itself fails - the failure handler then wrote "failed" over the cancellation and queued the next daily occurrence. `mark_finished` already guarded this; the start path must too.
- The DVR schedule file is a convenience, not the state. A write that fails (a full disk, a locked file) must never change a job's state: the write that records the running recording's id failing marked the job "failed", and the scheduler only stops jobs that are "recording", so ffmpeg kept recording past the end of the window and held the provider's one stream slot. The scheduler's writes go through `_save_schedule()`, which logs and carries on.
- The exit gate warns about each kind of work on its own. A scheduled recording and a running download both need a warning, and one must not hide the other: the download is truncated when the app exits, so the user has to be asked about it.
- Never wait on the GUI thread for a long job. The exit waited for a recording that was still finalizing, for the whole size-derived budget - an hour for a large faststart MP4 - with the window "Not Responding" and the screen reader silent. The wait runs on a thread; the shutdown's own loop keeps the window alive.
- An archive window has a clock, and it is the provider's, not UTC. Both URL styles must render on the same one: the path style honoured `catchup-timezone` while the template style filled `{H}` from the UTC instant, and Windows had no IANA database at all, so `ZoneInfo` failed and the PC's own zone was used silently. Ship `tzdata`, and test a wall-clock token, not only epoch ones.
- A missed archive probe must cost one request. A 403 on these panels means the account's stream is busy and a 404 means the file is not there; treating either as "server rejects HEAD" sent a ranged GET that opened the media the probe exists to avoid opening. Only 405 and 501 justify the fallback.
- A rename that fails is not a failed capture. `_settle_partial_output` deleted the finished `.part` when `os.replace` hit a locked target (scanner, share, open player) and the report still said the download completed, so the user lost the programme. Keep the bytes and report the `.part` path: the name is a convenience, the data is not.
- An exit code of 0 is not a recording. ffmpeg exits 0 when a stream closes before the first frame, so success must be the file having bytes - check it once and use that answer for both the message box and the DVR job's stored outcome.
- The track probe is the third recording start path beside manual and scheduled, and it has to clean up after itself. An exception on that worker thread left the key in `pending` for the whole session, so every later press said "stopping", nothing recorded, and the shared player was never resumed. Report on the GUI thread, drop the key, resume playback.
- First-run defaults must match what the installer ships. The default player was "VLC" while the build bundles libVLC, so a new user's first Play said the player could not be found; the playback code already fell back to "Built-in Player".
- A config that parses but is not an object is a corrupt config. The old loader returned defaults for `[]` without keeping the file, and the next save overwrote the user's playlists; valid-JSON-wrong-shape now takes the same "keep a `.corrupt` copy" path as a parse error.
- Two threads write the config (GUI and playlist worker) and the atomic replace has no ordering: without a lock the older snapshot can land last and silently revert a setting.

- Local live buffer (2026-10-27): retain original provider identity while recording through protected local live-edge cursors and explicit leases. Player Stop must not kill a recording-held ingest. Serialize direct recording startup with buffer owner registration; recheck provider occupancy inside that gate. Stale UI delivery must acknowledge ownership or close before next source startup. Quotas count incomplete writes and apply per source, not globally.
