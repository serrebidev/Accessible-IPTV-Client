# UI and accessibility

Moved here from `agents.md` on 2026-10-22, verbatim. `agents.md`
points at this file; read it before changing the code it names and
grep it for the module, symbol or error you are about to touch.

- Player Tab traversal must skip hidden and disabled controls, including the empty audio-track chooser. Handle Tab in the frame's key hook so the volume slider cannot hand focus to the video surface. Failed playback must disable both transport buttons and their menu items, guard transport shortcuts, and leave focus on an enabled control. Manual Stop must still offer Play.
- Search results must be installed before focusing/selecting a result. `_VirtualChannelList.replace_contents()` clears selection even when the new row count is unchanged; focus alone leaves a one-result search with no selected channel and an empty URL. Select the first installed result only while the channel list has focus, preserving the search-focus generation guard. `tools/smoke_playlist_navigation.py` checks Sky Mix via Enter and Tab, then two Tabs to its URL.
- If `.pytest-work` is left inaccessible after an interrupted elevated Windows test run, do not reuse it: pytest now uses the ignored `.pytest-runs` workspace-local base temporary directory. This avoids broken ACL cleanup while retaining the `conftest.py` suppression of Python 3.14's relative `*current` links.
- `wx.LogError` uses printf-style formatting. Escape literal percent signs before passing user/provider text into it.
- Replacing virtual channel-list search/group rows must clear the active selected/focused item state even when its numeric index remains in range. During a shrink, change the native item count while the old model still supplies every remaining row, then swap the model; during a grow, install the new model before increasing the count. This prevents NVDA/MSAA from querying stale or out-of-range virtual rows.
- The internal player's "Audio Track" submenu is rebuilt on `wx.EVT_MENU_OPEN`; bind that event on the frame and compare `event.GetMenu()` to the submenu (a `wx.Menu` cannot be used as a Bind source), and clear items with `menu.DestroyItem(item)` (not `Remove`, which leaves the C++ object alive).
- The category/group list must decouple *selection* from *activation* for NVDA: arrow keys (and Home/End/PageUp/PageDown/typing) only `event.Skip()` so the native listbox moves the highlight and NVDA announces it, while Enter/Tab/click activate. Do NOT repopulate the channel list or move focus from `EVT_LISTBOX` — on wxMSW that event is dispatched asynchronously, so a "suppress focus" flag set in `wx.EVT_CHAR_HOOK` is already cleared (via `CallAfter` or a `finally`) before `on_group_select` runs, and focus still jumps. Bind `wx.EVT_LEFT_UP` for mouse activation and call `on_group_select()` explicitly on Enter/Tab.
- Toggling a favorite must not call `_refresh_group_ui()`: that repopulates the channel list and pulls focus out of it, in the middle of the user working through the list. `_update_favorites_group_row()` inserts, relabels or deletes just that one row and fixes up the group-list selection index by hand.
- NVDA says nothing when a virtual list row's text changes underneath it, so the favorite marker alone is not feedback. `_VirtualChannelList.announce_item()` cycles only the focused state (`SetItemState` off, then on) for that row, which re-fires the focus event and makes NVDA re-read the row with its new text. Do not cycle the selected state as well: that re-enters `on_highlight` and re-runs the EPG lookup for no benefit. The marker is the word "(Favorite)" rather than a star glyph, because NVDA speaks nothing for most symbols at the default punctuation level, and it is suppressed inside the Favorites category where every row would carry it.
- A test run that finishes green and then appears to hang is wx waiting for a click. Tests exercise failure paths on purpose -- `test_add_provider_source_survives_a_dialog_that_cannot_open` feeds in a dialog class that raises -- and the production code answers with `wx.LogError`, whose default target under a GUI app is a *modal message box*. The box is queued, surfaces at interpreter shutdown with no event loop behind it, and blocks the process until someone dismisses it. From a terminal it looks exactly like an infinite hang: the suite reports all tests passed, then nothing. With a screen reader the stray dialog is worse than the delay. `tests/conftest.py` redirects wx logging to `wx.LogStderr`, which took the full run from 36s to 15s with a clean exit 0.
- Setting that log target once at session start is not enough: constructing `wx.App` installs wx's own GUI target and discards ours, so conftest re-checks it before every test body (a `pytest_runtest_call` wrapper, which runs after fixtures have built the app). `test_wx_errors_are_not_shown_as_modal_dialogs` asserts the redirect survived. Never restore the previous target afterwards: `wx.Log.SetActiveTarget` takes ownership of what it is given and deletes what it returns, so handing the old pointer back at teardown is a use-after-free that kills the interpreter with a Windows access violation.
- A synchronous Cast callback failure needs an error box owned by the built-in player and Cast button focus restored after dismissal, even when the app modal queue defers the box. GUI tests cover routing and focus; spoken behavior still needs manual NVDA/Narrator verification.
- On wxMSW, `SetName` alone does not name the Cast device list or Channel EPG list in native MSAA. Keep a `wx.StaticText` with the list's stable name immediately before each list control (adjacent auto IDs); `tools/smoke_accessible_names_nvda.py` verifies both real `accName` values.
- A button whose label changes must change its accessible name with it: the player set the Play/Pause label to "Resume" but kept the name "Play", so NVDA announced a button that no longer existed. Set the name from the label at every place the label is set, and assert `GetLabel() == GetName()` in the test.
- Binding `EVT_CHAR_HOOK`/`EVT_KEY_DOWN` on a control to add one key's behaviour must `event.Skip()` for every other key. The About dialog's hyperlinks opened the browser from an unconditional handler, so Tab (and each arrow key) launched a browser window while merely moving through the dialog. Note also that `wx.WXK_MENU` is Alt; the Applications key is `wx.WXK_WINDOWS_MENU`.
- A `wx.Dialog` consumes Enter before the focused control sees an `EVT_KEY_DOWN`, so Enter handlers on a list inside a dialog must use `EVT_CHAR_HOOK` (or a real default button). `CatchupDialog` had `EVT_KEY_DOWN` and no default button, so Enter on a catch-up programme did nothing at all.
- `get_config_read_candidates()` leads with `_config_write_target(create=False)`. Read order and write target used to be derived independently, and a portable build unpacked into a read-only folder read from the app directory while saving to `%APPDATA%` - so every settings change (a renamed playlist, say) reverted at the next start. `_config_write_target` takes `create` because `tests/test_startup_lazy.py` asserts that computing the read candidates does not create the user config directory.
- wxMSW gives a freshly shown dialog's focus to the first control in tab order, and a `SetFocus()` in the constructor does not survive that. `_SourceNamesMixin._focus_source_list()` therefore also queues a `wx.CallAfter`, which runs once the modal loop is up.
- Do not put backslash escapes (`\t`, `\n`) inside a bash heredoc that feeds a Python patch script in this environment: they arrive as real tabs/newlines and silently corrupt the patched source. Build them as `chr(92) + "t"` or write the script to a file first.
- F1 context help is wired once, on the `wx.App`, by `main.install_help_hooks`: an app-level `EVT_CHAR_HOOK` (the last stop of any unhandled key, in every window) and `EVT_HELP`. On Windows one F1 press arrives as *both*: the char hook fires, and even when it consumes the key Windows still sends `WM_HELP`, which wx turns into `EVT_HELP` for the focused control. `request_context_help` therefore drops a second request within 0.5 s. With a menu open there is no char hook at all, only `EVT_HELP`, whose event object is the menu's window (the frame, or the control a popup menu was shown on) and whose id is the *highlighted item's* id - that is how menu items get their own topics. That id comes from `HELPINFO.iCtrlId` as an unsigned 16-bit number: wx's automatic (negative) item ids arrive as 65536 minus the id (-31992 becomes 33544), so `user_guide.topic_for_menu_item` tries both forms. The menu must be closed *after* the `WM_HELP` handler returns (`wx.CallAfter` → `user32.EndMenu()`): a popup (context) menu ignores `EndMenu` called from inside the handler, stays in menu mode, and a guide opened then sits inside the popup's modal loop where Escape and every other key still go to the menu. `_show_when_menus_closed` also waits until `GetGUIThreadInfo` clears `GUI_INMENUMODE`/`GUI_POPUPMENUMODE` before opening the guide. `tools/smoke_user_guide_f1.py` drives all of this with real key presses. The app char hook runs before menu-bar accelerators, so `User Guide\tF1` on the Help menu shows the shortcut without stealing F1 from context help; a real click on the item (F1 not held) opens the guide at its start. Linux sends no `WM_HELP`; the char hook covers F1 there.
- The User Guide text box must be `TE_RICH2`. Its caret positions equal Python string offsets; a plain multiline EDIT counts each `\n` as two positions, so section jumps and Find selections land early by one character per line above them. Find lower-cases with a length-preserving fold (`str.lower()` turns a Turkish dotted capital I into two code points).
- Scheduler-thread notifications, including “Scheduled recording started”, must use `IPTVClient._show_or_queue_message_box()` through `wx.CallAfter`, never `message_box()` directly. A direct app-modal box can arrive while the user is still dismissing the scheduling confirmation and freeze wxMSW by nesting its message loop. The scheduled-recordings `wx.ListCtrl` intentionally permits multi-selection: Ctrl+A selects every row; Delete and Numpad Delete are silent for an empty list, otherwise they confirm the selected title (or “all” only when every displayed row is selected); and active selected jobs are stopped before deletion.
- The update helper's status window must manage focus, not just visibility (issue #30): when the app closes, focus falls to the desktop, and when the UAC prompt returns, focus goes back to the app that just exited - the TopMost status window was still on screen but to NVDA it had disappeared. `update_helper.ps1` now calls `Focus-StatusWindow` once when the parent process exits and once per `Update-StatusMessage` stage change (each grab makes NVDA read the new window title), while `Watch-StatusWindowFocus` (called from `Wait-Pumped`) latches `UserLeftStatusWindow` the moment `GetForegroundWindow` reports any other window, after which the update never takes focus back - the stage text still updates in the title for NVDA+T. A NULL foreground is the UAC secure desktop and never counts as the user leaving. Focus watching only starts after the first successful grab, or the app's own still-open progress dialog would be mistaken for the user switching away. The helper is staged from the *installed* build, so a helper fix only takes effect from the update after the one that ships it.
- Not every foreground change during an update is the user leaving (follow-up to #30). The silent installer's hidden windows take the foreground when it starts, and on Windows 11 the foreground can also stay parked on Explorer's invisible `ForegroundStaging` window; both used to latch `UserLeftStatusWindow`, so the status window was never re-focused, NVDA went silent for the install, and because the helper was no longer foreground the restarted app could not take focus and its "Update Complete" box went unread. `Get-ForegroundOwnerKind` now sorts the foreground into self / update (installer PID and its children, tracked in `$script:UpdateOwnedPids`) / neutral (no window = secure desktop, `consent.exe`, desktop, taskbar) / transient (`ForegroundStaging`, taken back after `TransientGraceMs`) / other (only this latches). Watching starts only once the window really held the foreground, `ForceForeground` uses `AttachThreadInput` when a plain `SetForegroundWindow` is refused, and `Grant-ForegroundToNextProcess` runs before the app is restarted. The "Windows will ask for permission" stage is shown only when `Test-ElevationPromptExpected` says a prompt will appear (EnableLUA, token elevation type, ConsentPromptBehaviorAdmin/User); UAC off or "elevate without prompting" announced a prompt that never came. This dev machine has `ConsentPromptBehaviorAdmin=0`, so an end-to-end run of the helper against the real installer with `/DIR` in %TEMP% and a dummy parent PID reproduces that setup; the log names every window that took the foreground.
- The app owns the cancellable download in one `wx.ProgressDialog`. Only after the installer is fully downloaded and verified does it launch `update_helper.ps1`, replace the dialog with a non-cancellable handoff message, and wait for the helper's `update_window_ready` marker before closing. Starting the helper before the download left both the helper and app windows alive and could strand keyboard focus between them. Keep the helper's current focus recovery, result reporting, and restart logic; only the download-to-helper handoff returned to the proven two-stage flow.
- The window holds its controls in `$script:StatusLabel`/`StatusProgress`/`StatusButton`, never `$form.Controls["StatusLabel"]`: that lookup returned null on a user's machine (issue #31 logged "The property 'Text' cannot be found on this object"), and because it threw on the first line of `Update-StatusMessage`, the title stopped updating and the window sat on one message for the rest of the update. `Get-StatusWindow` re-creates the window if it is ever lost, and `ControlBox = $false` plus a `FormClosing` handler mean neither Alt+F4 nor anything else can take it away while the update runs. The one button it ever shows is Cancel during the download and Close on a failure.
- The status window is now up while the app is still usable (it covers the download), so `Watch-StatusWindowFocus` can latch `UserLeftStatusWindow` on the *app itself*: someone who goes back to watching television during a 95 MB download used to disable every later re-focus, and NVDA then had nothing for the whole install. `Reset-StatusFocusLatch` reopens it at each moment the update becomes the user's task again - the install starting, a failure, a stop, and the final confirmation - and nowhere else, so a progress message still never pulls focus away mid-download.
- **Never synthesise an Alt keypress to take the foreground.** `_force_foreground` used `keybd_event(VK_MENU, ...)` - the well-known trick for unlocking `SetForegroundWindow` - and Alt is also what opens a menu bar, so the app pressed Alt for the user and left them in the menu instead of the channel list: at the end of every update, on every restore from the tray, and every time a second copy brought the running one to the front. `AttachThreadInput` (already there) is what actually grants the right; a test pins `keybd_event` out of main.py for good.
- A finished update takes its window away: `Complete-SuccessfulUpdate` says the update is complete, pauses `$script:CompleteLingerMs` for that to be spoken, hands the foreground to the restarted app and closes. No Close button - the update is over, and a button there is one more thing between the user and the application. Only the paths that have something to read keep `Wait-ForDismissal`: a failed or cancelled update, and an install whose app would not start.
- `wx.WXK_MENU` is Alt and `wx.WXK_WINDOWS_MENU` (395 on MSW) is the Applications key. `ScheduledRecordingsDialog._on_char_hook` handled `WXK_MENU`, so pressing Alt alone popped its context menu - the same trap `WhatsOnNowDialog._on_key` already documents. Its list also binds `EVT_CONTEXT_MENU`, so the Applications key and Shift+F10 work without the char hook; check every new dialog against this, and `tests/test_all_dialogs_build.py` builds the scheduled-recordings one.
- The Recording Format choice is saved for the kind of channel it was made on (`_set_recording_format(key, channel)`), and `recording_format_video` may name an audio preset (soundtrack only). Routing by the preset's own kind saved MP3 picked on a TV channel as the radio preference, so TV stayed MKV. Dialogs opened from the built-in player must be owned by the player, or closing them leaves it with no focus for NVDA.
- Do not rely on a dialog's `wx.ID_OK` button being the native default button: the "What's on Now" Play button carries no `BS_DEFPUSHBUTTON`, so wx had nothing to press for Enter, and a `wx.Dialog` consumes Enter before the focused control sees an `EVT_KEY_DOWN`. A list inside a dialog takes Enter from `EVT_CHAR_HOOK` (the catch-up and scheduled-recordings lists already do) - or the button is `SetDefault()`ed.
- An index over the whole channel list is built off the GUI thread, before the dialog that needs it appears. "What's on Now" resolves a programme's channel when it is played or scheduled, and building that index on the GUI thread freezes the app and silences the screen reader for seconds.
- Disabling the focused control leaves the player with no focus at all, so the focus moves to the next control instead. `wx.Window.FindFocus()` also raises when there is no application object, so it is asked through a helper that answers None.
- A details screen must distinguish "the server said never" from "the server said nothing". An empty account payload printed "Expires: Never (no expiry date set)" beside "Status: not reported by the server", so an unknown line was reported as a lifetime one. Same rule for a numeric status: a raw digit is not a word, and "Status: 0" tells a screen-reader user nothing.
